# Hardening checklist (platform- and stack-neutral)

Each item is a **goal** plus an **acceptance criterion**. The criterion is what counts; the mechanism is whatever the platform and stack offer. `audit.sh` uses these IDs; a row `<id>:<ecosystem>` or `<id>/<setting>` is a sub-item of `<id>` and shares its criterion (`scripts/test-checklist-ids.sh` keeps the two in sync). When a platform or stack has no native mechanism, look up its current docs, pick the closest equivalent, and record the gap in the report.

Scope column: **local** = works with plain clone access; **repo-write** = needs push/PR rights; **admin** = needs repository admin; **registry** = needs the user's own registry account and 2FA (never done by the agent).

| ID | Goal | Acceptance criterion | Scope |
|---|---|---|---|
| `hooks.protect-branch` | Nobody commits or pushes straight to the default branch by accident | `pre-commit` and `pre-push` block `main`/`master` (and `feat:main`, deletes); `ALLOW_MAIN=1` bypasses; `scripts/test-hooks.sh` exits 0 | local |
| `hooks.secrets` | Secrets are caught before they leave the machine | `pre-commit` runs a secret scanner (gitleaks, trufflehog, detect-secrets…) on staged changes; on by default (installed if missing), the user may decline in the go-ahead | local |
| `hooks.hygiene` | Unresolved merges and large binaries never get committed by accident | `pre-commit` blocks staged conflict markers (`<<<<<<<`/`>>>>>>>` at line start) and new files above a limit (default 500 KB, `git config hooks.maxFileKB`; Git LFS files skipped): `assets/githooks/pre-commit`, or `check-merge-conflict` + `check-added-large-files` from `pre-commit-hooks` with the framework; on by default, the user may decline or change the limit in the go-ahead | local |
| `hooks.quality` | Lint/format errors are caught before commit and broken tests before push | `pre-commit` runs the project's formatter check + linter on **staged files only** (never `.`, `{all_files}`, a whole-repo `npm run lint`, or a framework hook with `pass_filenames: false`), reading what is committed: a hook manager's staged mechanism (lint-staged, lefthook `{staged_files}`, the `pre-commit` framework), or without one `run_staged` from `assets/githooks/staged.sh` (NUL-safe, deleted files skipped, partially staged files refused); `pre-commit` stays fast (aim under ~5 s on a typical commit) and offline: no typecheck, tests or network calls; `pre-push` runs the project's typecheck + tests (the same commands CI runs); only tools the project already configures (no new linter installed without asking); added to the existing hook manager if there is one, after the branch check; `--no-verify` bypasses; on by default, the user may decline or keep only `pre-commit` in the go-ahead; `n/a` when no stack is detected | local |
| `hooks.installed` | The hooks the repo declares actually run, in this clone and in a fresh one | every hook type the repo declares (manager config, `.husky/`, a versioned hooks dir) is an executable in the active hooks dir that calls the manager; the `pre-commit` framework lists every stage it uses in `default_install_hook_types` and runs without `core.hooksPath`; a fresh clone activates them automatically (`prepare`/`postinstall`) or the activation command is in README/CONTRIBUTING; `n/a` when no hooks are declared | local |
| `deps.vulns` | No known vulnerable dependency ships | the ecosystem's audit tool reports 0 (fix without forced major bumps; report leftovers) | local |
| `deps.bot` | Dependencies, CI actions and hooks get update PRs | Dependabot or Renovate config covers **every** detected ecosystem plus the CI actions ecosystem, plus `pre-commit` when `.pre-commit-config.yaml` has remote hooks (Renovate: opt-in `"pre-commit": {"enabled": true}`); security updates grouped as `security-patch-minor` (patch/minor) | repo-write |
| `ignore.git` | Secrets, dependencies and build outputs never reach git | the repository's own ignore files (a global `core.excludesFile` or `.git/info/exclude` does not count) ignore `.env`, `.env.*`, `*.pem`, `*.key` and each ecosystem's dependency/cache dirs (`references/ecosystems.md`), and leave `.env.example` versionable; after install + build + test in a `/tmp` copy, `git status --porcelain --untracked-files=all` is empty; every tracked secret-like file is either a fixture (kept, reason recorded) or untracked in the PR with its rotation listed for the user (history is never rewritten) | repo-write |
| `ignore.docker` | A container build context carries no secrets, history or local dependencies | every Dockerfile/Containerfile has a `.dockerignore` (`<Dockerfile>.dockerignore`, its directory's, or the root one) that excludes `.git`, `.env*` and, for Node, `node_modules`, or is an allowlist (`*` then `!` re-includes); `n/a` without a Dockerfile | repo-write |
| `ignore.publish` | A published package ships only what it needs | the package dry-run (`npm pack --dry-run`, an sdist listing, `cargo package --list`) contains no `.env*`, keys or local config; npm packages declare a `files` allowlist (an `.npmignore` replaces `.gitignore`, so it easily leaks); `n/a` when nothing is publishable | repo-write |
| `ci.pipeline` | Every change is validated before merge | a pipeline on PR/MR and on the default branch runs install + the project's validation (test, typecheck, lint, build); read-only token; job has a **fixed name** | repo-write |
| `ci.pinned` | CI and hooks cannot be hijacked through a moved tag | every third-party action/image/component is pinned to a full commit SHA/digest with the version in a comment; every remote `pre-commit` framework hook is frozen the same way (`rev: <sha>  # frozen: vX.Y.Z`, written by `pre-commit autoupdate --freeze`); tools a hook or setup step installs are pinned to a version, never `@latest` | repo-write |
| `ci.pr-title` | The squash commit message follows the repo's commit convention | when the repo has a convention (commitlint/commitizen/release tool config, or ≥ 80 % of the last 20 commit subjects are Conventional Commits), a `pull_request` workflow (types include `edited`) validates the PR title, which becomes the squash commit; no checkout, no token, title passed through `env:`; fixed job name, added to the required checks; the skill never installs a `commit-msg` hook (an existing one is kept); `n/a` without a convention | repo-write |
| `automerge` | Security fixes land without waiting, but only when CI is green | bot PRs in the scope chosen in the go-ahead (default: `security-patch-minor` with semver patch/minor; never major) get auto-merge; the job never checks out or runs PR code; guarded by repo name and same-repo head; **install only when `protect.branch` requires the CI checks** (otherwise auto-merge merges before CI) | repo-write |
| `publish.oidc` | Releases are published without long-lived tokens | publish job uses the registry's Trusted Publishing / OIDC (`id-token`), no registry token secrets, provenance/attestations when the registry supports it, tag validated against the version and the default branch history | repo-write |
| `publish.npm-repository` | npm provenance links the package to this repository | `package.json` `repository.url` is `git+https://<host>/<owner>/<repo>.git` for this repo (npm only) | repo-write |
| `publish.registry` | The registry trusts only this repo's publish workflow | a trusted publisher (workflow + environment) is registered for the package on each target registry; afterwards token publishing is disallowed and old tokens revoked | registry |
| `publish.env` | Only release tags can reach the publish credentials | publish job uses a deployment environment restricted to the release tag pattern (`v*`) | admin |
| `merge.squash` | Linear, readable history | squash is the only merge method; squash commit = PR title + body; branches deleted after merge; "update branch" enabled; auto-merge allowed | admin |
| `protect.branch` | The default branch only changes through validated PRs | no deletion, no force push, PR required (0 approvals for solo devs), squash only, required checks = CI job name(s), strict/up-to-date policy; admin bypass only through PR | admin |
| `protect.tags` | Published releases cannot be rewritten | release tags cannot be deleted, moved or force-pushed; admin bypass; tag creation restricted to admin and the detected release tool, unless the user declined | admin |
| `protect.signed` | Every commit on the default branch has a verified signature | an active rule requires signed commits on the default branch (GitHub: `required_signatures` in its own ruleset); enabled only after this run's PR is merged and once the user's own commits are verified; on by default, the user may decline in the go-ahead (unsigned commits on a PR head branch block even a squash merge, so every contributor must sign) | admin |
| `secrets.scanning` | Leaked secrets are detected and blocked server-side | secret scanning + generic (non-provider) patterns + push protection + automatic security updates enabled; where the platform lacks it, a required CI job running a secret scanner is the fallback | admin |
| `review.bot` | Every PR gets an automated code review before merge | the default branch requests an automated reviewer on every PR and push: Copilot code review through a `copilot_code_review` ruleset rule with `review_on_push`, or a review App (CodeRabbit…) installed and configured in the repo; advisory only, never counted as an approval; reviewer chosen in the go-ahead | admin |
| `classic-protection` | One source of truth for branch rules | no legacy branch protection overlapping the ruleset (migrated and removed by default, unless the user declined) | admin |

## Out-of-reach items
When an item exceeds the user's scope, leave it unapplied and add a **maintainer recommendation** to the report: what to enable, where, and why, in a form the user can forward (issue/MR description).
